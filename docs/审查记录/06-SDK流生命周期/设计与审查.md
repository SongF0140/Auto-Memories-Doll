## 设计取舍

1. 保留所有常见 AiEvent 名称。仅增加可选 callId/success/error/status/hasToolErrors 和 signal；JSONL schemaVersion 仍为1，历史快照兼容。终态 status 为 completed/failed/aborted。
2. SDK error → error(status:failed)；abort → done(finishReason:abort,status:aborted)；finish → done，未知或错误完成原因标 failed。异常 EOF → error，不猜测成功。首个终态封口，不再转发后来成功或重复终态。
3. SDK tool-error → tool_call_result(success:false,error,callId)，工具失败可恢复，仍可继续文本并 completed，但 hasToolErrors 阻止画像自动分析。内置业务失败及 MCP 抛错返回失败对象，而非伪成功错误字符串；MCP isError 也识别为失败。不扩展完整 MCP 输出协议。
4. 请求 signal 保持同一个对象穿过 Route → Dispatcher → Handler → Adapter → Provider；provider 为 reader.cancel 自有控制器与请求信号做 AbortSignal.any 合成，保证下游取消也终止 SDK。合成信号语义相同但不声称 SDK 端与 request.signal 身份相同。
5. stream-adapter 中共享 wrapAiStream 供 adapter、handler、session、SSE 复用：一次终态、finally releaseLock、cancel 向上游传播、abort 唤醒读循环、取消时不向已关闭 controller 写入。
6. 会话保留已有部分助手文本保存行为，增加可选 status/hasToolErrors；取消保存 aborted，异常保存 failed。去重包含元数据，避免相同正文吞掉终态变化。没有助手文本时维持既有不追加助手快照行为。
7. 将提前画像分析延后到正常终态 finalizer；失败、取消、工具失败、异常 EOF 和离线降级不分析。非流收集同样检查终态并释放 reader。
8. 两个入口复用 SSE 包装但保持原 Content-Type：普通 /api/chat 为 text/plain; charset=utf-8，/api/chat/stream 为 text/event-stream。JSON 分支保持原语义。
9. ModelPool 仍只限制流创建，不改为覆盖完整消费。FakeProvider 同步可选 signal 和预取消。

### 门禁后发现：嵌套清理取消覆盖终态

主代理进一步检查实际多层路径：Provider → Adapter → Handler → Session → SSE。合成诊断（`88c517`，只加载纯流模块，不访问数据库/模型）显示，body 输出 `done.status=completed`，但 adapter、handler、session 三层 finalizer 均收到 `cancelled:true`。根因是每层收到终态后执行 `reader.cancel("terminal received")`，下一层也执行同样清理；已有 `cancel` 把清理取消与终态前用户取消混为一类。Handler 因此跳过成功画像分析，Session 可能把已观察的 completed 覆盖为 aborted。

本次修复仍使用已披露并实际加载的 `systematic-debugging`、`test-driven-development`，属于 A06 终态不可回退与 finalizer 竞态范围。先补嵌套包装 finalizer 和 Session → SSE 的失败回归；拟采用“终态一经观察不受后续清理取消改变”的最小方案，保留取消对 reader 释放及停止写 controller 的行为。替代方案是把所有上游清理删除，但可能造成终态后的未读数据和 reader 留存，故不采用。测试通过后重新从针对性测试、治理测试到完整门禁串行验证；前节绿灯仅证明修复前版本。
