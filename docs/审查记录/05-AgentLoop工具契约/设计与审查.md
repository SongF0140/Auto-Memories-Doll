## 架构事实与根因

当前调用链是 `ChatHandler → ModelAdapter → OpenAIProvider → AI SDK streamText`。真正多轮模型/工具循环由 SDK 管理；`orchestrator.ts` 是后台审核与落库，不是聊天 loop。既有 `isStepCount(readonly ? 1 : 5)` 保持不变；`readonly` 的一步上限不等于工具写权限控制。

Tau 采用单轮 provider 配合显式循环。本块参考其契约边界，不整套移植架构，也不把历史入口描述直接当作当前运行事实。

旧描述返回 `tool.schema._def`，Handler/Provider 继续将其作为参数 schema 传给 SDK。`_def` 是 Zod 内部描述，不是完整 Zod schema；真实 SDK 把它走到 lazy schema 调用，产生 `TypeError: schema is not a function`。

## 方案、替代方案与成本

1. **采用最小修复**：描述返回 `tool.schema`，返回类型从 `object` 收窄为现有注册表使用的 `ZodTypeAny`。沿用同一校验真源，无新依赖、无重复 JSON Schema、无公共接口扩张。
2. **不手写 JSON Schema**：避免字段/默认值双份维护和遗漏 Zod 本地校验。模型端 JSON Schema 与本地 refinement 不完全等价，不能宣称转换后模型端表达全部规则。
3. **不重写显式 AgentLoop**：现有 SDK 已管理循环，重写会扩大步数、事件、错误及取消的验证范围，超出批准切片。
4. **测试成本**：六项转换覆盖全部内置工具，三项拒绝测试覆盖空值、越界与纠错定位约束；利用已安装 SDK，无联网调用。测试保留 `FlexibleSchema` 类型断言，因此不将其宣称为额外的静态兼容性证明；运行时仍使用真实 SDK 转换与 validator。
5. `ZodTypeAny` 是 Zod4 的兼容别名，本块与现有注册字段一致，不借修复扩大类型迁移。
