## 来源证据

- `src/lib/ai/ai-events.ts`：`tool_call_result` 已有可选 `data?: unknown` 字段（"UI/日志侧结构化结果；模型只消费文本 content"），事件契约无需扩展。
- `src/lib/ai/openai-provider.ts`：`toSdkInputSchema`/`toSdkTool`/`isNormalizedEnvelope` 已定义未接线；`generateStream` 内联 `tool({inputSchema: t.parameters})` 直接消费普通对象（MCP 场景在 SDK prepare-tools 转换中崩溃）；`tool-result` case 丢弃信封 `data`。
- `src/features/chat/handler.ts`：内置工具成功时返回裸 `result.data`（丢失 content 文本），MCP 成功时返回原始 `callTool` 结果（无信封）；MCP 抛错已返回 `{success:false, error}`。
- `src/__tests__/ai-tool-boundary.test.ts`：`toSdkTool` 返回 `Record<string, unknown>` 导致测试中 `toModelOutput` 为 unknown，4 处 TS18046。

## 设计取舍

1. 模型通道与结构化通道分离：模型只消费文本（成功信封 → text，失败信封 → error-text，裸字符串 → text，其他对象 → json），由 `toModelOutput` 承载；UI/日志侧结构化 `data` 由 `tool_call_result` 事件承载。两通道来源同一 execute 返回值，不做第二次转换。
2. 信封判定单一来源：provider 与 handler 共用「对象含 success 字段即信封」判定；`success === false` 或 MCP `isError === true` 为失败。信封失败置 `hasToolErrors`，阻止画像自动分析（沿用第六块语义）。
3. handler 统一归一化：内置工具把 ToolCaller 的 `{toolName, success, content, error, data}` 映射为信封（成功带 data，失败保留 content/error）；MCP 成功结果提取 text content 作为 content、原始结果整体作为 data；MCP `isError` 按失败信封归一化；抛错维持失败信封。schema 交接仍走第五块 `toSdkInputSchema` 契约。
4. `toSdkTool` 返回类型收窄为含 `toModelOutput`/`inputSchema`/`description` 的结构化类型，消除测试侧 unknown 断言错误；不引入运行时行为变化。
5. 不改变第六块流生命周期语义：tool-error 仍映射 `tool_call_result(success:false)`；done 仍按 finishReason 判定 status。
