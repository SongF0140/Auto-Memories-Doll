# 09 — 统一聊天入口、显式操作与增量学习任务设计与审查

## 授权、范围与状态

2026-10-04，依据批准路线第 09 块（统一聊天入口、显式操作与增量学习任务）在已获授权的 main 工作树实现。未安装依赖，未访问真实密钥、真实模型、真实网络和私人数据库（测试全部使用 mock env / mock 服务 / 临时目录 SQLite）。读取批准路线、dispatcher/classifier/handler/两 route/chat-session-service/database 现状。本块加载 test-driven-development、ponytail。

本块目标：a) 显式记忆操作只允许来自整条斜杠命令（/remember、/search、/correct、/delete <id>）或 UI 结构化 action，彻底移除自然语言关键词截获与 embedding 语义猜测；删除/纠正必须带明确 ID，缺定位不得自动 top1；b) /api/chat 与 /api/chat/stream 统一走 AgentDispatcher 调度；c) 新增对话增量学习任务表与生命周期（幂等入队、单次取出、失败不重试、中断恢复），本块只入队不产出知识（真实分析留待第十块）；d) 新表仅加法迁移。不动 ChatHandler → ModelAdapter → Provider 调用链，不动 domain 层设计。

## 来源证据

- dispatcher.ts（旧）：classifier 返回 memory_create/memory_query/memory_delete 等意图类型，Layer1 关键词 includes（"删除/记录/记住…"）+ Layer2 embedding 语义回退——"今天学习了删除文件的命令 rm -rf"会命中删除意图，属误触事故路径。
- 两 route 调度不一致：/api/chat 走 AgentDispatcher（意图路由），/api/chat/stream 直连 ChatHandler.streamResponse——同一输入在两个入口行为不同。
- env 无学习任务表：对话结束后无持久化增量学习入口，ProfileUpdater 仅做画像分析且不入库任务状态。
- IntentResult 旧类型含 alternatives/matchedKeywords 供 system-prompt 意图块渲染——意图块随关键词截获一并废弃。

## 设计取舍

1. **classifier 收窄为斜杠命令判定**：`IntentType = "chat" | "system_command"`，仅 `/` 开头（confidence 0.95）判定为命令，`entities.command` 携带整条命令行；其余一律 chat。classifyAsync 与 classify 同构（保留异步签名兼容既有调用方）。budget LLM 实体提取 extractMemoryEntity 保留，供显式创建命令结构化辅助。
2. **显式操作双通道、删除/纠正必须 ID**：dispatcher 的 action 参数优先（UI 结构化操作，validation.ts `chatActionSchema` discriminatedUnion：create/query 带 text、update/delete 必带 memoryId）；否则按整条斜杠命令分发。`/delete <id>` 与 `action:{type:"delete"}` 都要求 ID：空 ID 拒绝并提示、ID 不存在返回"未找到"、绝不语义定位 top1。`/correct <id> <指令>` 同构，CorrectionService 按 memoryId 定位。
3. **命令轮次不入队学习任务**（独立审查 Major-1 统一）：显式命令/结构化 action 是确定性操作（删除、检索、纠错），不是需要沉淀知识的 AI 对话轮次——两条 route 的 JSON 分支均不入队，杜绝 `/delete` 回显被当作学习素材污染知识库。
4. **学习任务生命周期**：`conversation_learning_tasks(turn_id TEXT PRIMARY KEY NOT NULL, …, status CHECK queued/processing/completed/failed)`；`enqueueCompletedTurn` prompt 模式跳过、turnId 唯一约束幂等（重复→duplicate）；**不用 INSERT OR IGNORE**——它会把 NOT NULL 等约束违规也静默吞掉（better-sqlite3 把 undefined 绑定成 NULL），改为 plain INSERT + 仅捕获 UNIQUE 冲突返回 duplicate，其余错误向外抛（失败不谎报保存）。`processNextLearningTask` 单任务取出→processing→completed/failed，处理器抛错记摘要不重试；`recoverInterruptedTasks` 启动时仅 processing→queued。
5. **完成钩子只判 completed**：ai-events 的 terminalStatus 已把 degraded 映射 failed、abort 映射 aborted，钩子无需重复判定降级。`createTurnLearningHook` 生成服务端 turnId（`turn-<uuid>`），入队失败仅 warn（"不影响聊天响应，不伪造已保存"）。
6. **会话正文不复制**：ChatSessionService（JSONL）仍是正文真源，任务表只存本轮 user/assistant 文本与状态，符合"SQLite 为长期知识真源、派生不复制"约定。
7. **worker/scheduler 沿用既有后台模式**：worker 启动时恢复中断任务 + 10s 轮询 processNextLearningTask；scheduler 注册进 instrumentation，启动日志标注 "/ learning"。本块不注入处理器（任务保持 queued），第十块接入真实价值判断。
8. **意图块废弃**：system-prompt.ts 删除 buildIntentBlock 死代码（新 IntentResult 无 alternatives），SystemBlocks.intentBlock 字段保留恒空串，组装模板零行为变化。

## TDD 命令与红灯证据

统一命令：

```text
npx vitest run src/__tests__/conversation-learning-service.test.ts src/__tests__/agent-dispatcher-commands.test.ts src/__tests__/chat-route-learning-hook.test.ts src/__tests__/classifier.test.ts
```

实现前登记 4 个测试文件（新增 3 + classifier 重写），红灯合计 34 失败，全部因目标行为缺失：

1. conversation-learning-service（11 用例）：无表/无服务 → 全部失败（入队、幂等、状态机、恢复、入队失败抛错）。
2. agent-dispatcher-commands（8 用例）："今天学习了删除文件"/"记录功能怎么用"走对话流零操作、/delete 缺 ID 拒绝、/remember 显式创建等 → 旧 dispatcher 关键词截获触发错误分支。
3. chat-route-learning-hook（7 用例）：stream route 无统一调度与钩子 → dispatch 断言失败。
4. classifier（重写 10 用例）：旧 classifier 对"帮我更新一下…"返回意图对象而非 chat → 断言失败。

绿转期修复（每项先复现失败再修）：

- **vitest 陷阱**：`afterEach(vi.restoreAllMocks())` 会清掉模块级 vi.fn() 的 mockImplementation，第 2 个用例起 dispatcher 变空对象报 "close is not a function"→ 删除 afterEach，仅 beforeEach `vi.clearAllMocks()`。
- **INSERT OR IGNORE 吞约束**：turn_id 加 NOT NULL 后"入队失败抛错"仍不抛——OR IGNORE 把 NOT NULL 违规也静默化（changes=0）→ 改 plain INSERT + 仅捕获 UNIQUE 冲突（node 实测 better-sqlite3 12.x 把 undefined 绑定成 NULL，plain INSERT 抛 SqliteError）。
- **lastUserMsg 未定义**：删除意图分类死路径时误删 streamResponse 的 `lastUserMsg` 定义，3 个画像分析用例报 ReferenceError → 补回（与 generateResponse 同构）。
- **波及用例清理**：chat-handler.test 中"memory_create 意图触发 extractMemoryEntity"/"extractMemoryEntity 抛异常"两用例测的是已删除行为 → 删除，classifier mock 一并清理；pipeline integration 的英文创建用例原靠 embedding 语义回退触发 → 改为 `/remember pipeline content` 全句命令（classifier 桩与真实实现同构）。
- **typecheck 拦截**：system-prompt buildIntentBlock 引用已删除的 `IntentResult.alternatives`（TS2339）→ 删除死代码；EnqueueResult 联合的 `.reason` 直接访问（TS2339）→ toEqual 精确断言；DispatchResult 联合 `as {data}` 强转（TS2352）→ expectJson 收窄辅助。
- **lint/format**：未用 storedTask 辅助删除（--max-warnings=0）；6 文件 prettier --write 后复检通过。

## 独立审查与修复

独立只读审查结论：无 critical。1 major + 3 minor + notes，处理如下：

| 编号 | 问题 | 处理 |
|---|---|---|
| Major-1 | 双 route 对命令 JSON 轮次入队不一致：/api/chat 不入队、/api/chat/stream 合成流后钩子会入队，且测试只覆盖前者 | 已修：stream route 显式命令（result.type==="json"）跳过钩子；用例改为"两条 route 一致"双断言（chat 与 stream 的命令轮次都不入队，stream 仍正常回包） |
| Minor-1 | processNextLearningTask SELECT 后 UPDATE 非原子认领 | 记录边界：当前单 worker 串行消费（SQLite 单连接同进程），无并发消费路径；第十块注入真实处理器仍走同一单 worker，届时如需多实例再改认领式 UPDATE |
| Minor-2 | 命令解析大小写敏感；任意 `/` 开头文本被劫持为命令返回帮助 | 帮助文案补一行"以 / 开头的消息都会被当作命令处理"提示契约代价；大小写敏感记录为已知行为 |
| Minor-3 | UI action 不受 mode 约束（prompt 模式也可 delete/create） | 记录取舍：显式操作是用户主动行为，契约未禁止跨模式；保持现状 |
| Note | UNIQUE 冲突靠错误消息字符串匹配（版本脆）；钩子每轮 new Service() 重复幂等 DDL；worker 无处理器空转轮询 | 均记录，无实质风险（单连接、单 worker、进程退出有兜底） |

审查通过项：日志仅记 turnId/reason/error message 不含对话正文；任务表存本轮文本属设计内；"今天学习了删除文件/记录功能怎么用"由真实 classifier（非 mock 自证）验证不触发写删；降级/取消不入队、入队失败不伪造保存符合契约。
